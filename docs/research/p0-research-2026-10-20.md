# Apophenia — targeted research decisions (20 Oct 2026)

Status: **external research + engineering recommendations**. These findings expand `plan-audit-2.md` without overriding its user decisions. No device benchmark, Android APK build, real transcription, or objective sound-quality evaluation has happened in this workspace.

## Source of truth and scope

`original-design/plan-audit-2.md` wins when any previous plan disagrees. Product: Apophenia, offline-first GPL-3.0 Android application, app id `audio.apophenia` **provisional until approved**. P0 probe and mockups; P1 capture engine + persistent rail + widget/tile/shortcuts; P2 music core/Workshop/take analysis; P3 Stacks/Connections; P4 piano/theory; P5 transcription; P6 player; P7 notation; P8 offline speech; P9 practice/exercise/export.

No USB audio, pedal, volume-key binding, string-mode tuner UI, sessions builder, or mandatory second piano dynamic in early phases. Instrument is **selected**, not audio-classified. Audio analysis is not AI.

## R1 — tempo + key / mode detection, short phone takes

**Tempo, firm design recommendation**

- Store the metronome state, tick sample-frame positions, beat emphasis, time signature and any tempo-map changes **as a provenance-linked beat grid** with the take when a click is running. This is an exact record of the reference **click**, not an assertion that every note played on that beat.
- Without click, use amplitude-energy flux plus spectral-flux onsets, followed by inter-onset-period histogram / autocorrelation of onset strength and beat-grid consistency. Return ranked BPM values (e.g. `92`, `46`, `184`) and a `free/unreliable` state; do not force a number.
- Do not conflate note subdivision with quarter-note pulse. Musical meter and beat unit matter (e.g. dotted quarter vs quarter; 6/8), as do sparse attacks and rubato. A tempo value alone does not establish a starting beat grid.
- The initial `TempoCandidates` reference implementation uses onset lattice-fitting; it is **not** a calibrated beat tracker. Replace/benchmark it before shipping P2.
- Tests: hand-clapped or plucked at 50, 72, 92, 120, 160 and 200 BPM; eighth-note subdivisions, syncopation, offbeats, held notes, free-time takes; 5 / 10 / 20 / 60 seconds; count-in/click present vs absent. Prefer an explicit `uncertain` result over false confidence.

**Key and mode, firm design recommendation**

- Monophonic: take stable notes from transcription → duration-weighted chroma. Chordal: apply log-frequency STFT/chroma, harmonic suppression/whitening to reduce overtone false notes, and group per beat/bar before aggregation.
- Rank 12 tonics × all 7 major modes first, then harmonic and melodic minor modes per the larger shared theory catalog. Use scale membership **and** genuine tonic evidence: recurring phrase-final notes, bass pedal, cadential resolution, weighted phrase beginnings/endings, manually assigned key. Explain evidence rather than merely emitting a confidence percent.
- Relative modes have **identical pitch-class collections**. Even perfect pitch extraction cannot disambiguate C Ionian from D Dorian without a home-note clue; a short riff may remain `tonic unclear / mode uncertain` indefinitely. Never use mode names as certainty signals when the evidence is absent.
- Chromatic passing tones, blue notes, borrowed chords, modal mixture and pitch bends can break simple scale templates. Store alternatives and let user correct key and mode independently.
- `ModeEvidence` currently validates the ambiguity concept for seven major modes only; harmonic minor / melodic minor mode families still need catalog integration in P2/P4.

Sources: [Essentia beat-extraction methods](https://essentia.upf.edu/tutorial_rhythm_beatdetection.html), [librosa's onset→tempo→beat pipeline](https://librosa.org/doc-playground/latest/generated/librosa.beat.beat_track.html), [Essentia key-profile options and genres](https://essentia.upf.edu/reference/streaming_Key.html).

## R2 — single-note transcription and chord recognition

**Mono capture**

- Track pitch in overlapping windows with a YIN family estimator (or aubio) and voicing confidence; use the instrument-selected lowest string as pitch-search floor with margin, not a visible string mode. Onsets from amplitude and spectral novelty split repeated same-pitch notes. Fuse pitch and onset before quantization.
- Bass A0=27.5 Hz has period ≈36 ms. A 3–4-period observation takes ≈109–145 ms, so a 20-ms window **cannot** properly resolve the lowest bass notes. Favor offline after-take transcription accuracy over live latency, adapt the analysis window with instrument range, and never pretend subbass from a phone mic is guaranteed.
- For each note store `{startSeconds, endSeconds, midiPitch, frequency, confidence, sourceTakeId, sourceTimeRange, uncertain}`; derive notation with key spelling and derive tab using tuning/capo/nearest-hand-position chooser. Never treat transcribed MIDI pitch as an enharmonic spelling decision.
- Quantize only when user requests it or a recorded beat grid exists; keep the original time positions for tap-to-audio replay; allow manual corrections and recalc connections from corrected rather than guessed notes.
- After human review, measure onset ±50 ms, note semitone error, duration deviation, false split rate and octave errors, separately for bass/guitar/voice and quiet/noisy environments. Track results not just the successes.

**Chord blocks**

- Compute chromagram every short frame, aggregate over stable segments/beat windows, match root+quality templates from shared theory catalog, penalize missing tones and energy outside template, smooth changes with persistence/hysteresis. Return top candidate chord names and **No reliable chord** if ambiguity is high.
- A `C/E` inversion is **not** determined by chroma alone (need separately estimated bass). `Cmaj7` and `Em/C` can sound similar; missing fifths, extensions, detuning and distorted spectra make uncertain names normal.
- Strumming produces rapid sequential notes; stabilize across time, do not label every 50 ms. This approach yields *chord labels*, not individual fingerstyle/piano voices.
- `ChordTemplates` prototype works on supplied ideal chroma arrays only, *not* recorded guitar chords. An STFT/chroma extractor is not yet implemented.

**Polyphonic note-by-note transcription**

- Spotify's [Basic Pitch](https://github.com/spotify/basic-pitch) is Apache-2.0, with ONNX/TFLite serialized models, but its reference workflow is Python and a model asset alone cannot run on Android. Need a packaged Android inference runtime, DSP pre/postprocessing, ABI-matched `.so` (if used), phone performance/memory test, and license notices. [Supported runtimes and model formats](https://github.com/spotify/basic-pitch/blob/main/basic_pitch/__init__.py).
- P0 `System.loadLibrary` test verifies whether **one tiny ELF shared library** can be packaged/loaded. It does **not** verify Basic Pitch, TensorFlow Lite, operator compatibility or successful polyphonic transcription. Remain a P5 optional path until separately measured.

Sources: [YIN reference paper](https://pubmed.ncbi.nlm.nih.gov/12002874/); [aubio pitch/onset/notes functionality, GPLv3+](https://github.com/aubio/aubio); [Spotify Basic Pitch Apache 2.0 and runtime list](https://github.com/spotify/basic-pitch/blob/main/README.md).

## R3 — time-stretch / pitch-shift for Stacks

**Recommended implementation: offline render/cached playback.** Stack changes and live capture should never run an expensive stretcher inline in the low-latency audio callback. Store original source PCM and render conformed mono/stereo WAV/PCM in a worker after edits. Loop exactly on bar grid, crossfade seams, compensate algorithmic lead/trailing padding before writing rendered duration, mix up to eight layers via a light engine.

Libraries:

| Choice | License | Findings | Action |
|---|---|---|---|
| [Rubber Band](https://breakfastquay.com/rubberband/license.html) | GPL-2.0-or-later (can be used under GPLv3) | Independent pitch/time control; R2 faster, R3 generally better on complex bass/vocals but more CPU; C wrapper/Android legacy examples exist | **Quality candidate** after ARM64 compile/runtime proof; test R2 then R3 offline |
| [SoundTouch](https://soundtouch.surina.net/) | LGPL-2.1 (can be used in GPL project with proper compliance) | Time-stretch and pitch change, Android examples and efficient operation | **Fallback/benchmark**; check transients, smearing, bass fidelity, source/relinking obligations |
| Simplistic sample-rate conversion | Internal | Cheap but changes tempo **and** pitch together | **Not acceptable** as the stack conform engine |

- Exact tempo factor convention: input 92 BPM → stack 96 BPM means output duration/input duration = **92/96 ≈ 0.95833**, i.e. shorter; changing key by +2 semitones is a separate parameter. Label deltas `92→96 BPM, +2 st`.
- **Do not auto-shift** an audio layer whose key/tonic is unknown, or when the target does not specify a compatible tonal center. Give the user a zero-shift/manual decision; do not infer transposition from an unverified mode tag.
- Conservative initial UI quality guidance (engineering starting point, not an empirically established limit): within ±8% tempo and ±2 semitones = generally safer; ±20% / ±5 semitones should prompt audible A/B check; no hard blocking. Evaluate clean bass notes, vocals, drums/transients and reverb separately. Test edge crossfade click and exact frame count over repeated looping.
- Cache key should include source take digest/id+revision, sample rate, trim frames, target grid+tempo map, transposition cents, engine/version/quality settings. Invalidate on any changed input. Keep source immutable; cache must be regenerable and safely cancellable.
- License review before shipping: Rubber Band's GPL supports GPLv3 application, but check **all linked FFT/resampler dependencies** and Android distribution terms; SoundTouch's LGPL requires compliance and relevant relinking provisions. No third-party binary is bundled in this starter besides the P0 self-built ELF marker.

Sources: [Rubber Band author licensing](https://breakfastquay.com/rubberband/license.html); [Rubber Band R2/R3 discussion](https://github.com/breakfastquay/rubberband); [SoundTouch official features](https://soundtouch.surina.net/); [SoundTouch LGPL notice](https://www.surina.net/soundtouch/README.html).

## R4 — lyric-to-melody fit and pronouncing dictionary

- [CMUdict](https://github.com/cmusphinx/cmudict) is freely usable and redistributable; include attribution and keep its license/notice when bundling it. Its US-English ARPABET entries mark vowels with `0` unstressed, `1` primary, `2` secondary stress, and often contain alternate pronunciations (`WORD(1)`). Don't conflate CMUdict **data** with [cmudict-tools](https://github.com/cmusphinx/cmudict-tools), which is separately GPL-3.0-or-later licensed.
- For each lyric line: tokenize preserving contractions; look up **all** alternate pronunciations; produce per-syllable stresses; syllable count and suffix from last stressed vowel are suitable offline features. Unknown word/name? Mark its pronunciation `unknown` and offer tap-to-edit / manual syllable breaks, **not** an arbitrary guessed perfect rhyme.
- For each melody phrase: extract note onsets, strong metric positions, duration/held notes and phrase boundaries. Use sequence alignment / dynamic programming between syllables and note events: penalize lexical stress on a weak musical beat, allow melismas (one syllable spanning several notes), slurs, pickup and rests, and distinguish accent of **beat** from arbitrary high note. Suggest multiple ranked placements, not a magical `line definitely fits` declaration.
- Rhyme: tail from the last stressed **vowel phoneme through word end**, not spelling. End-rhyme and internal-rhyme suggestions should show their phoneme reason. Same lexical pronunciation may vary in actual singing; user choice wins.
- Prototype `LyricProsody` handles syllable stresses and simple 1-to-1 or 1-to-2 melismas, and `PronouncingDictionary` reads alternate word entries; these are for tests, not tuned to real sung rhythms or yet stocked with the actual dictionary data.
- When later bundling the full dictionary: create a compressed indexed representation during the build, not a many-object full text map allocated during every lyric query. Measure startup RAM / asset size and keep asset out of user backups if rebuildable.

Sources: [CMUdict repo and redistribution statement](https://github.com/cmusphinx/cmudict), [CMUdict tool licenses (different code)](https://github.com/cmusphinx/cmudict-tools).

## Dependencies and deliberate non-decisions

1. Neither the chord-template prototype nor the pitch-YIN scalar prototype is a production recording-to-MIDI implementation.
2. No final library selection for stretch/pitch until 2–3 real recordings have been A/B checked on a phone; preference is Rubber Band if compliant and packagable, SoundTouch if simpler/better in the actual measurements.
3. No Basic Pitch integration until tested on the actual ARM64 phone with a real native/inference model; prebuilt-library loading alone is an insufficient test.
4. No hard `mode` for short ambiguous riffs. User correction is always a first-class input, cached with analysis provenance.
5. Do **not** use CMUdict as a semantic mood classifier. Mood comes from user folders/tags; this is explicitly a rule-driven app.

## Suggested recording metadata contract for P2

```text
TakeMeta {
  id, audioFileUri, sourceIdeaId, durationFrames, sampleRate,
  selectedInstrument {kind, tuningId, capo, fretCount},
  clickGrid? {clickFrames[], accents[], beatUnit, signature, tempoChanges[]},
  tempo {valueBpm?, halfAndDouble[], status: click|estimated|free|unknown,
         analysisVersion, evidence, correctedByUser},
  tonal {tonic?, mode?, candidates[], evidence[], confidenceBand,
         status: corrected|estimated|ambiguous|unknown},
  analysisState: pending|running|complete|failed,
  createdAt, updatedAt
}
```

When user corrects a value, prefer the correction over any rerun. Don't coerce free-time takes to a fictitious grid. Transcription notes and chords remain linked to audio-time ranges and have provenance flags.
